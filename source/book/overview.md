# 《STL源码剖析》整书理解

## 来源与目的

侯捷《STL源码剖析》，用户提供的简体中文扫描 PDF，共 542 个物理页。出版年份尚未从版权页确认，不能用文件的 2012/2016 年元数据代替出版年。剖析对象是 SGI STL、GNU/Cygnus C++ 2.91.57；不是现代 C++ 全部标准库的规范。正文、序言和附录区分记录，网站广告不进入知识池。

目标：从原书形成可调用的 STL 源码阅读、状态推演、复杂度及前置条件核验能力。先解释结构，再检查代码和分支，最后通过独立算例或编译实验验证。采用与参照项目一致的 single-first 交付：一个发现入口，内部原子能力卡；公开仓库仅保存原创解释、短引文、工具、测试及审计，不分发扫描件和全文 OCR。

## 一句话主旨

STL 通过明确的迭代器与对象语义契约，把储存、算法和操作策略解耦，再利用编译期分派与数据结构不变量实现可复用且高效的组件。

## 骨架及其关系

1. 第1章（PDF33–76）：说明六组件及具体实现版本，建立“规格与实现分开”的阅读入口。
2. 第2章（PDF77–115）：把储存配置与对象构造分开；小区块配置、未初始化内存算法为容器提供底层操作。
3. 第3章（PDF116–149）：以迭代器隐藏容器布局，以 traits 和 tag dispatch 将关联型别、能力及优化分支传给算法。与第2章构成互相引用的基础。
4. 第4、5章（PDF150–322）：vector/list/deque/heap 与树、哈希表提供不同储存和遍历契约；以字段不变量、插入删除状态变化解释代价。不能把容器名当性能结论。
5. 第6章（PDF323–452）：算法仅依赖所需迭代器能力；copy、集合操作、查找与排序各有范围、顺序和生命周期前提，优化必须守住这些语义。
6. 第7、8章（PDF453–500）：函数对象承载策略，配接器改造接口，把前面的组件拼接起来；容器、迭代器和函数三种配接不能混淆。

附录（PDF501以后）保留书目、站点与旧工具链移植的历史背景，不把历史编译器修补当现代构建建议。

## 术语与核心主张

- allocator：原书区分字节储存管理与对象生灭，SGI `alloc` 不是标准 `allocator<T>` 的同名替代。
- iterator：算法访问对象的操作契约，不等同于连续地址，也不等同于带虚函数的公共基类。
- traits：把关联型别和性质转成编译期可选择的信息；原生指针通过特化参与。
- 半开区间：`[first,last)` 包含首位置而排除尾位置；尾位置用于停止判定，不能因此解引用。
- invariant：数据结构在操作前后必须维持的关系，本项目用来组织原书的指针及旋转图解。
- function object：携带可调用行为的对象；可以保存状态，旧式 adaptable typedef 另属历史接口。
- adapter：改变已有组件暴露的接口，使同一底层机制服务不同用法。

原书的推进不是“记住六组件名称”。allocator 分离生存期，容器才能管理尚未构造的容量；迭代器分离遍历，算法才能跨储存结构复用；traits 恢复必要信息，通用代码才不必放弃适当的优化；仿函数及配接器则把可变策略和接口继续分离。

## 批判与边界

SGI 的 128-byte 小区块阈值、8-byte 分档、vector 扩容策略和 deque 缓冲布局都是该实现的事实，不能写成所有标准库必须如此。书中配置器讨论明确简化多线程，不能推出线程安全。类型的旧式 POD/trivial 标签不构成对任意对象执行 memcpy 的许可。红黑树、哈希表及排序代码用于理解所列机制，不证明任何未知仓库实现必然正确。现代接口、失效规则、保证及移除的适配器需要另查当前标准或目标库实现，并单独标注补充来源。

# 补充参考边界

- **f06 内存不足处理例程的重试协议**（§2.2.5，PDF91–94）：第一级配置请求失败后，不直接假定所有内存都不可用。 若客户设置了处理例程，先调用它，再重试配置。 未设置处理例程则按该实现的异常或终止策略退出。 要区分operator new使用的new-handler与SGI在malloc之上仿真的机制。 重试是否有进展取决于处理例程，不能承诺一定成功。

- **f10 类型性质驱动的安全优化分派**（§3.7，PDF140–149；§6.4.3，PDF358–364）：从当前操作真正需要的性质出发，例如析构或赋值是否平凡。 读取该实现记录的类型标签，选择保守路径或优化路径。 用户自定义类型未登记时，旧SGI倾向采用保守分支。 不得从类看起来简单推导出可以随意字节复制。 原书的内部__type_traits与现代标准类型特征要分开使用。

- **f14 deque端点增长与map扩充的分离**（§4.4.5–4.4.6，PDF189–203）：端点插入先检查当前缓冲区是否仍有可用位置。 辅助路径先保证map能容纳新增缓冲区，再配置缓冲区并构造元素。 端点删除在合适条件下释放空缓冲区，清空仍保留初始布局所需缓冲区。 中间插入和删除要分析搬动方向与两侧距离。 不能把不搬整个元素区误解为永远没有内部管理结构重配置。

- **f15 用底层容器接口构成受限容器**（§4.5–4.6 PDF204–208；§4.8 PDF220–222；§8.2 PDF474）：先确定所需访问纪律，再选择能提供必要操作的底层容器。 stack暴露栈顶操作，queue分离入队和出队两端。 priority_queue再加入heap维护，而不是简单更名一个顺序容器。 检查每个公开操作如何委托到底层及维护规则。 不暴露任意遍历与修改有助于维持其访问纪律。

- **f17 二叉搜索树旋转与红黑插入修复**（§5.1–5.2，PDF239–270）：先按键比较找到插入位置，再检查颜色与黑高约束。 依父、伯父和祖父关系选择变色、单旋或双旋。 旋转必须保持中序关系，并更新父链和根连接。 SGI额外使用header保存根、最小和最大节点的入口。 修复结束后同时核对查找顺序、颜色约束和header，不只画出似乎平衡的树。

- **f20 从具体数组查找到泛型算法**（§6.1.5–6.2，PDF330–336）：先识别算法真正使用的操作，而不是它最初服务的容器。 将数组大小改写为首尾范围，将指针改写为支持所需操作的迭代器。 失败以last表示，从而跨容器保持一致的停止语义。 参数名表达算法要求的最低迭代器类别。 泛化应保留可达性和有效范围前提，不能由模板替调用者保证。

- **f28 partial_sort的有界候选堆**（§6.7.8，PDF425–427）：需要前k个最小元素有序时，只维护k个候选而不排序全体。 先把候选区构成最大堆，使当前候选中的最大值便于替换。 扫描其余元素，遇更小者替换堆顶并修复。 最后把候选堆排序得到有序前缀。 剩余尾段的内部顺序不在该任务保证中。

- **f31 nth_element的单侧分割选择**（§6.7.12，PDF449–450）：目标是某个秩位置的值与完整排序一致，而不是排序前缀。 分割后根据nth落在哪一侧，只继续处理该侧。 待处理区间足够小时用插入排序收尾。 核对nth两侧的比较关系与多重集合保持，不能要求同一个具体排列。 与partial_sort的区别在于是否要求前缀内部有序。

- **p02 半开区间与可达的尾位置**（§1.9.5、§6.1.5，PDF73、330–333）：以[first,last)描述访问范围；循环先比较尾位置再解引用。区间必须可由first按所需操作到达last；first==last是空范围。不能把源码解释中的last-1照搬到只支持递增的迭代器。

- **p06 小区块归还自由链表而非立即还给系统**（§2.2.7–2.2.8，PDF97–101）：配置时弹出对应链表头，释放时把区块挂回对应头部；客户占用期间不再由自由链表指向。deallocate必须匹配原大小档，释放并不等于系统堆立即减少。此为历史SGI机制。

- **p11 类型性质只在满足语义时许可快速分支**（§3.7、§6.4.3，PDF140–148、358–364）：区分iterator_traits与SGI __type_traits，后者记录默认构造、复制、赋值、析构、POD等性质。历史保守默认会令自定义类走逐元素分支；不能为了快而随意把带资源对象标成trivial，也不能把这些内部类型名当公共标准接口。

- **p24 关联式容器优先使用其成员查找**（§5.3–5.4，PDF275、280）：generic find按迭代器逐一遍历，不了解树结构；成员find使用索引结构。先区分相等比较语义，再比较操作复杂度；不可宣称所有成员函数都更快。

- **ce01 混用标准allocator与SGI alloc接口**（§2.2，PDF82–89）：把以类型参数工作的标准allocator接口直接套到原书SGI字节配置器，或反过来。

- **ce02 构造异常后遗漏已成功构造的部分**（§2.3，PDF106–108）：批量构造在中途抛异常，先前构造成功的对象仍存活而清理路径已退出。

- **ce03 内存不足处理未设置或无实际释放能力**（§2.2.5，PDF93–94）：把分配器内的重试机制误解为无条件保证分配成功。

- **ce04 vector扩容后继续使用原迭代器**（§4.2.5，PDF159–160）：保存旧begin或元素地址，扩容之后仍用它访问容器。

- **ce05 把list擦除节点的迭代器仍视为有效**（§4.3.3，PDF166–167）：把链表插入时迭代器稳定的性质套到已删除节点。

- **ce06 list splice位置落入被转移范围**（§4.3.6，PDF175–178）：同一链表中转移一段节点时，目标位置落在该段内部。

- **ce07 对无随机访问能力的容器调用通用sort**（§4.3.6、§6.7.9，PDF179、428、436）：因为list能遍历就认为它能作为通用sort的输入。

- **ce08 将deque逻辑连续误当作所有对象物理连续**（§4.4.2–4.4.3，PDF181–186）：以单一裸指针跨过deque缓冲区，或假定其迭代器只存cur。

- **ce09 给容器配接器强加遍历或任意排序接口**（§4.5–4.8、§8.3.2，PDF205–208、222、478）：因底层deque/vector有begin/end，就认为stack、queue、priority_queue也应直接暴露这些接口。

- **ce10 没有先追加元素或建立堆就调用堆维护算法**（§4.7.2，PDF211–219）：把push_heap当作自动分配/插入，或直接在任意无序区间上调用sort_heap。

- **ce11 pop_heap后忘记缩小容器**（§4.7.2，PDF215）：认为pop_heap已经删除最大元素，随后继续以全区间作为堆。

- **ce12 无平衡条件的搜索树退化**（§5.1，PDF239–241）：仅检查左小右大就保证所有查找O(log N)。

- **ce13 随意修改有序容器中的键**（§5.3–5.4，PDF271、276–282）：把set元素或map的key当作可任意修改的普通值。

- **ce14 C字符串键使用地址相等代替内容相等**（§5.8–5.9，PDF311–316）：希望按文字合并或查找键，却直接用默认指针相等。

- **ce15 单次哈希遍历看似有序就推导排序保证**（§5.8，PDF312–313）：用一次递增输出证明hash_set自动排序。

- **ce16 未满足合法区间与迭代器能力前提**（§6.1.5，PDF330–333）：传入无效迭代器或无法从first递增到last的范围，依靠“能编译”证明调用有效。

- **ce17 只有第二起点的双范围算法读过第二序列尾端**（§6.4.2、§6.7.1，PDF347、352、408）：旧式equal/mismatch/transform等只收到第二起点，却把长度更短的第二序列交给它。

- **ce18 copy写入空目标或容量不足的目标**（§6.4.3，PDF357）：对空容器begin使用普通copy，期望自动增长目标容器。

- **ce19 重叠区间的复制方向错误**（§6.4.3–6.4.4，PDF354–367）：向右重叠移动仍逐项从前向后copy；或反向情形错误使用copy_backward。

- **ce20 将无序hash容器直接交给有序集合算法**（§6.5、§6.7.1，PDF367、370、372、375、388–392）：因为容器名含set，就认为可直接做set_union等算法。

- **ce21 向Compare参数传入任意二元布尔函数**（§6.7.1 includes，PDF388–390）：只检查签名能返回bool，就把任意关系作为有序算法Compare。

- **ce22 remove或unique之后仍把原end之前全部当结果**（§6.7.1，PDF395–410）：调用算法后忽略返回的新尾，认为物理容器已经删除元素。

- **ce23 把unique当作未经组织的全局去重**（§6.7.1 unique，PDF409）：序列1,2,1调用unique后期望只剩1,2。

- **ce24 从inplace_merge名字推出零辅助空间**（§6.7.11，PDF442–443）：以函数名宣称实现不配置缓冲，或未先把相邻两段分别排好序。

- **ce25 无push_front接口却使用front_inserter**（§8.3.1，PDF475–477）：把所有插入配接器当作对所有容器通用。

- **ce26 把reverse iterator的base当成当前元素**（§8.3.2，PDF478–481）：认为*r等于*r.base()，或用只有单向能力的slist迭代器反向遍历。

- **ce27 输入迭代器构造早于提示语而提前等待**（§8.3.3，PDF482–483）：以为istream_iterator构造只是保存流引用，把提示语放在构造之后。

- **ce28 SGI扩展配接器误当成所有标准库接口**（§8.4.3，PDF493）：把compose1/compose2直接用于目标标准库而不查可用性。
